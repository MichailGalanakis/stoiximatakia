## HTTP contract

All writes require exact `APP_ORIGIN` and `X-SkillBetting-Client: web-v1`. All responses use `Cache-Control: no-store`. Unknown signup fields remain rejected. The new session/Demo/logout writes accept only an empty JSON object; caller-supplied IDs, roles, contacts, credits, passwords, or verified flags are rejected.

| Operation                  | Behavior                                                                                                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/registrations` | Existing validated form. Atomically creates user, registration token, and independent account token. Adds `account` to the existing response; sets both cookies. Rotates/revokes the presented older account session.                                                    |
| `GET /auth/session`        | Read-only `{account}` or `{account:null}`. No implicit creation, sign-in, or email/SMS send.                                                                                                                                                                             |
| `POST /auth/session`       | Uses a valid older registration cookie to establish an account session explicitly. If already signed in, returns the current account without issuing another token. Missing/expired registration credentials return 401. Used when an existing registration is reopened. |
| `POST /auth/demo`          | Reuses an existing signed-in account (including a registered account). Otherwise creates a temporary account and session, returns `{account}`, and clears the browser's old registration cookie. No messages are sent.                                                   |
| `POST /auth/logout`        | Revokes the presented account and registration tokens in one SQL statement and expires both cookies. Other devices' independent sessions are unchanged. Returns `{account:null}`. The large wallet logout controls now call this endpoint.                               |

Account shape: `id`, `username`, `kind` (`registered` or `demo`), `email`, `phone`, `emailVerified`, `phoneVerified`, `demoCreditsMinor`. There are no passwords, hashes, tokens, roles or identity approvals in the response. `demoCreditsMinor` now reports the single ledger's available balance, excluding reservations. Both creation paths grant new accounts 25,000 minor units (250 credits); existing balances are preserved. Funded ticket/reservation operations exist under the platform API; public grants, refill, deposits and withdrawals remain unavailable.

`GET /auth/registration` and code operations can also identify their own registered user through the account session after the original registration cookie expires. A Demo session returns no pending registration and cannot initialize or send contact codes. The older registration cookie alone is not accepted by `GET /auth/session`; its explicit upgrade requires a protected POST.

## Persistence and temporary credentials

Migration `003_account_sessions.sql` adds `account_kind`, non-cash Demo credits, and `account_sessions`. Existing users remain registered accounts with their original contacts, terms, and verification flags. Applied migrations 001/002 are unchanged. Session insertion failures roll back the entire new account; a partially created account is not returned as signed in.

The account cookie contains an independent random 32-byte opaque token. Only its SHA-256 digest is stored. Cookies are HttpOnly, SameSite=Lax, Path=/, with a fixed 30-day expiry checked by PostgreSQL. HTTPS uses Secure and `__Host-sb_session`; local HTTP uses `sb_session`. There is no sliding refresh. The original 24-hour registration cookie remains independent. No credentials are stored in browser localStorage/sessionStorage or returned in JSON. Password login and logout from the large wallet are now implemented; recovery, session management, and account conversion remain separate. See [profile and navigation](profile.md).

Each Demo user receives a random `Demo_<16 hex characters>` username and an unrecorded random 32-byte password, stored only as a salted scrypt hash. Mandatory email/phone storage uses unique internal placeholders: `<UUID>@demo.invalid` and `demo:<UUID>`. The phone placeholder is deliberately not a routable phone number. The database requires these exact namespaces for Demo users, keeps both verification flags false, and does not claim that participation terms were accepted. Ordinary signup still requires valid E.164 phone, real-form validation, and explicit terms acceptance; its email cannot use the Demo namespace. Contact reservation rejects Demo users independently of the controller guard.

Demo access depends on the cookie. Deleting it, logout, or expiry loses access; the unknown password and internal placeholders provide no recovery path. The account row remains stored; retention/cleanup and conversion to a registered account are future work. Repeated clicks with a valid session reuse the account; the UI also guards pending/double clicks. Independent tabs with no shared session yet can create separate temporary accounts; cross-tab exactly-once creation is not claimed. Both creation paths share the existing ten-per-hour hashed connection-IP limit and two-hash concurrency bound. The Docker backend now explicitly trusts one controlled edge hop; Caddy overwrites forwarded client IPs. Native development keeps proxy trust disabled.
