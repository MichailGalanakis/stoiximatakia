# Chess rules engine

Editable, headless engine owned in this repository following the owner's takeover request on 1 November 2026, based on the unchanged v0.1.6 delivery identified in [SOURCE.json](SOURCE.json). Original supplied archives remain in Downloads. The reusable verification kernel remains **0.3.0 / schema 1 / `skillbetting.chess.fide-2023.v2`**. The registered multiplayer profile is **0.4.0-strict.2 / schema 3**, described below. Generated builds stay ignored; source archives and permanent regression fixtures are retained.

From the backend repository, run `npm ci` and `npm run test:chess`. This builds ESM/CommonJS, checks consumer declarations and runs the engine suite. The root lockfile pins the shared TypeScript compiler and development-only chess.js movement oracle. `npm run check` includes engine and backend validation.

## Rules and integration boundary

The engine owns legal actions, deterministic transitions, immutable serializable state, replay, observations and chess outcomes. Authentication, actor/seat binding, private access, transaction/revision control and settlement belong to the backend. `PlatformModule` registers only `ArtifactChessGameRuntime` when a database is configured; migration 009 supplies its durable proof storage. Backend registration does not assert public deployment status; see the [backend checkpoint](../../docs/backend-progress.md).

Default `createGame` and `createAnalysisGame` remain 0.3.0 library APIs and are not registered for multiplayer. Analysis roots establish local legality, not historical reachability. The inline proof profile **0.4.0-strict.1 / schema 2 / `skillbetting.chess.fide-2023.strict-proof.v1`** remains an unregistered profile for analysis and regression use. Neither older profile can be relabelled into an artifact snapshot.

Public observations contain complete accepted move coordinates and standard algebraic notation (`moves[].san`). Offers, claims and hypothetical proof moves never become played moves; private receipts and artifact references never enter player observations. One game is one engine round and match. There are no chess clocks or computer-play implementation in this integration, and it does not claim complete FIDE tournament functionality. Platform forfeits use the separately agreed automatic opponent win policy, rather than the inherited guarded resignation/adjudication API. Only final outcomes enter settlement.

## Registered artifact profile

**0.4.0-strict.2 / schema 3 / `skillbetting.chess.fide-2023.strict-proof-artifacts.v1`** pins the 0.3.0/FIDE-v2 verification kernel. Root and every physical board move require a checked mate-reachability decision before acceptance. Unchanged-position draw commands reuse preceding references while history-based claims and automatic endings remain authoritative in the shared reducer. There is no unresolved continuation or additional adjudication/pause state.

`prepareArtifactGame` and `prepareArtifactAction` return immutable candidates backed by private preparation context. `finishArtifactCandidate` accepts only a genuine, matching checked artifact binding. `restoreArtifactState`, `replayArtifact` and `getArtifactObservation` require checked bindings for every reference and never run search. Missing/cloned handles, mismatched roots/revisions/versions, unused references and relabelled histories fail.

Snapshots store compact per-revision references containing artifact identity, movement root, kernel pins and stream format; they contain no proof body or verdict in those references. `bindVerifiedArtifact` requires a genuine same-module streaming decision. Trusted repository code first binds that token to the exact sealed manifest and chunk chain; an artifact hash or JSON flag is never proof authority. Publication, binding and candidate completion occur within the same worker.

The backend worker owns preparation, durable search, independent checking and both player views. Bounded guided searches and a bounded, memory-guarded breadth-first probe import only verified positive mating witnesses. If those attempts find none, a fair PostgreSQL frontier continues the finite movement-graph search without a semantic cutoff. Search checkpoints and immutable proof chunks survive interruption. Cold restoration checks the stored stream again instead of trusting builder flags or a stored verdict. The backend rechecks authenticated actor, roster, source snapshot, action and revisions before an atomic game/ref commit.

Capacity, cancellation, memory, storage and input failures prevent acceptance; they never establish deadness, invent an outcome or permit uncertainty to continue as accepted play. Computation can require substantial time and storage. This proof search establishes mating possibility, not playing strength.

The older inline profile exposes `prepareStrictGame`, `prepareStrictAction`, `finishStrictCandidate`, `restoreStrictState`, `replayStrict` and `getStrictObservation`. Its receipts stay private and are verified without search on replay, but inline verification retains limits of 100,000 graph positions/expansions, 2,000,000 edges and 16,000,000 snapshot/evidence characters. It accepts no legacy/analysis roots, resignation or administrative actions and is not the registered execution path.

## Cooperative reachability and checking

`solveMateReachability(fen, limits?, certificates?)` asks whether either player can reach checkmate through any cooperative legal continuation. It ignores repetition and move counters for this possibility question, preserves castling/legal en-passant identity, and never continues past board mate/stalemate. Sufficient material/blocker/temporal/joint-king certificates prune only established dead descendants. Default analysis budgets are 4,096 positions, 256 unresolved expansions and 8,192 edges; cutoff returns `unknown` without evidence. These bounded APIs are not the artifact profile's acceptance policy.

`expandReachabilityPosition` gives the durable builder one deterministic expansion: mate with its winner, a sufficient leaf with a checker-compatible node, or the complete canonical successor set with one legal representative move and normalised child FEN per key. Every variant carries kernel pins and movement identity. Backend code does not reimplement chess movement.

Successful evidence is either a legal mating witness or a closed successor graph. `verifyReachabilityEvidence` snapshots stable JSON, reconstructs legal successor sets and recomputes all certificate leaves. It rejects missing/open/duplicate/unreachable nodes and wrong root/version bindings. `verifyReachabilityDecision` extracts a frozen `dead`/`not-dead` decision from that same verified snapshot, avoiding mutable-input verdict changes. Both keep the bounded inline verifier's input limits.

`verifyStreamingReachability` checks separately framed header/body records in `skillbetting.chess.reachability-stream.v1`. Per-header and per-record limits bound parsing memory; there is no total proof node/edge/move/JSON cutoff. The checker registers unique canonical nodes, independently traverses from the root, re-expands complete successor sets and recomputes static leaves. It rejects mate in a dead graph, missing/duplicate/extra nodes, corruption and incomplete streams. Witness checking retains one board and normalises irrelevant counters. Invalid proof provides no verdict; storage/source errors and aborts throw. Successful frozen tokens include the checked root, kernel, format and engine-owned decimal counts.

Graph checking requires a fresh, exclusive `PrivateReachabilityWorkset` with membership/frontier/visited storage separate from builder marks and counts. It preserves exact registered bytes, atomic uniqueness/visited marks and reliable queue membership. The optional `checked(position)` hook runs only after node mathematics and all successor operations succeed; it supplies no verdict, and a storage failure prevents success. The PostgreSQL adapter uses immutable chunk locators and digests. `isVerifiedStreamingReachabilityDecision` recognises only genuine same-module/worker tokens, never cloned JSON.

`createMateReachabilitySearch(fen, certificates?)` retains an in-memory frontier across `advance(maxEdges)` slices, including partially expanded nodes. A slice returns `pending` without evidence or a witness/closed graph; repeated positive slices are exhaustive over the finite graph subject to memory. `findMateReachabilityWitness` supplies deterministic legal playouts with cycle removal; optional `pawn-bait-before-capture` ordering changes only move ordering. Every positive line is checked, and failure means only `unknown`. The in-memory `solveMateReachabilityExactly` drives these helpers without a semantic cutoff; the registered runtime uses the separate durable frontier for its complete fallback. None implements a computer opponent.

The default 0.3.0 automatic-outcome path retains its bounded structural/solver scheduling. Older `analyzeDeadPosition`/`proveDeadPosition` APIs retain their original discovered-node budgets, so their metrics differ from the separate position/expansion/edge counts above. These compatibility paths do not govern registered artifact play.

## Correctness and operational limits

The reviewed v0.1.6 miss and published bishop/pawn proof game are immediate draws. The latter ends at its first dead move, **109 Bcxe2**, before the supplied construction continuation. A generic finite joint-king certificate proves frozen walls whose only possible breaches immediately stalemate; erased same-complex bishops are over-approximated by owner-only waiting. Independent movement closure, colour/reflection variants and live bishop/discovered-mate counterexamples test the sufficient theorem. `analyzeKingCorridor` is diagnostic evidence that must be recomputed.

Sufficient detectors alone do not recognise every dead position. Registered artifact play therefore requires a checked positive witness or complete/static proof instead of treating an unsupported detector result as permission to continue. The verifier shares the engine move generator and sufficient provers; chess.js tests give additional independent movement evidence, not a formal proof of those components.

Snapshots require their exact original engine, rules and schema versions. Limits remain 50,000 history records, FEN counters at 1,000,000 and snapshot JSON at 16,000,000 JavaScript characters; streaming proof size is separate. Resource failures are atomic errors, never outcomes or permission to discard history. Clock support and computer playing strength are outside this integration.

Rules reference: [FIDE Laws of Chess, effective 1 January 2023](https://handbook.fide.com/chapter/E012023), especially immediate endings in 5.2.1–5.2.2. Current validation and deployment status belong in the [backend checkpoint](../../docs/backend-progress.md).
